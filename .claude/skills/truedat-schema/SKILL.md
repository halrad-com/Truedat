## mbxmoods.json schema (current)

Per-track JSON object under `"tracks"[path]`. Feature fields fall into **15 core** (always present) + **40 extended** + **15 tonal/rhythm** + the authenticity blocks; extended and later fields are nullable — missing means the key is omitted, not written as `null` — plus metadata/identity fields. README's *Feature set* section carries the exact counts and how to re-measure them. **Do not maintain a total by hand here:** this line read "55 numeric feature fields" for months after the 2026-07-22 tonal/rhythm wave added 15 more, because a hand-kept number has nothing to check it and reads as authoritative while being wrong. What matters for decisions is the structure below — which fields are always present, which are nullable, and which are Essentia-derived and therefore neither backfillable nor in the re-extract canary.

- **Core features** (always present): the 15 fields `WriteTrackEntry` always emits (the names are in `FieldPrecision` and README's *Feature set*).
- **Tonal/rhythm extension wave (2026-07-22, nullable, omit-when-missing)**: `keyVotes` (nested block — all three key profiles `krumhansl`/`temperley`/`edma`, each `{key, scale, strength}`; the flat `key`/`mode` come from edma), `bpmFirstPeak`/`bpmFirstPeakWeight`/`bpmFirstPeakSpread`/`bpmSecondPeak`/`bpmSecondPeakWeight`/`bpmSecondPeakSpread` (tempo-histogram peaks — half/double-time evidence), `chordsKey`/`chordsScale`/`chordsHistogram[24]`/`chordsNumberRate`, `tuningFrequency` + 3 tuning-temperament scalars, `averageLoudness`. **Essentia-derived → NOT backfillable and NOT in the re-extract canary**: fresh analyses populate them, legacy entries simply lack them until a deliberate re-analysis. Primary consumer: AutoQ Camelot/harmonic mixing (key confidence + agreement) and tempo matching.
- **Harmonic-texture wave (2026-08-09, v0.5.4.7, nullable, omit-when-missing)**: `hpcp12` (12-semitone chroma vector — the extractor's 36-bin `tonal.hpcp.mean` folded 3→1 per semitone by `FoldHpcp36To12`, normalized to unit max, 4dp; **null on a no-chroma/silent track** so absence never fakes an all-zero similarity vector) and `dynamicComplexity` (`lowlevel.dynamic_complexity` scalar, 4dp), plus the **capture-once** ride-alongs grabbed on the same pass: `thpcp12` (transposition-invariant chroma — `tonal.thpcp` folded the same way as `hpcp12`; the extractor rotates it so the strongest pitch class sits at index 0, which is often but not always the tonic, so never read index 0 as "the key"), `beatsIntervalMean`/`Stdev`/`Min`/`Max` (inter-beat-interval summary in seconds from `rhythm.beats_position` via `BeatIntervalStats`, a compact beatgrid signal not the raw tick array), five frame `.stdev`s (`spectralCentroidStdev`/`spectralEnergyStdev`/`dissonanceStdev`/`pitchSalienceStdev`/`hpcpEntropyStdev` — within-track variability), and for speech `zeroCrossingRateStdev` + `mfccStdev[13]` (per-coefficient MFCC stdev = √ of the emitted `lowlevel.mfcc.cov` diagonal via `MfccStdevFromCov`). All were already computed by the extractor and dropped at parse — no extractor change, no extra compute. **Essentia-derived → NOT backfillable and NOT in the BASE re-extract canary** (same posture as the 2026-07-22 wave): fresh analyses populate them; existing entries stay tier-1 cache hits and lack them until a deliberate re-analysis (`--refresh-features`, whose staleness gate keys on `dynamicComplexity` — the always-emitted marker — so one pass populates the whole capture-once set without looping on silent tracks). **There is no parse-only backfill** — the raw extractor JSON is written to a per-track temp file and deleted at parse in `AnalyzeWithEssentiaCore`'s `finally`, so populating an existing catalog is a normal (byte-reading) re-analysis, not a cheap re-fold. Primary consumer: MBXHub AutoQ's harmonic-texture continuity term (cross-track `hpcp12` cosine) plus a small dynamics term (`dynamicComplexity` delta) — a preference weight beside Camelot, never a gate; the blend is null-safe, so a half-populated catalog behaves exactly as today. `thpcp12`/beats/frame stdevs are captured now and wired into picking later (.8+ hub-side); `mfccStdev`/`zeroCrossingRateStdev` + the frame stdevs also feed speech/transcription work. **This is the capture-once close** — the schema does not reopen unless a new *dependency* capability (vocal detection / fingerprint) is added.
- **Timbre arrays** (nullable, omit-when-missing): `spectralContrastCoeffs[6]` / `spectralContrastValleys[6]` (`lowlevel.spectral_contrast_*.mean` — per-band peak/valley contrast, timbre texture), `beatsLoudnessBandRatio[6]` (per-band share of beat loudness) and `gfcc[13]` (`lowlevel.gfcc.mean`, the gammatone-filterbank complement to `mfcc`). Same Essentia-derived posture as the two waves above: fresh analyses populate them, no parse-only backfill. `bpmHistogram` was cut from this group (see the emission registry below).
- **Extended** (nullable, omit-when-missing): the 40 extended fields (names in `FieldPrecision` / README *Feature set*: dynamic range, the loudness envelope, silence rates, spectral shape, Bark/ERB/Mel band stats, rhythm/tonal scalars) plus the Phase 2.5 `bitUsage` block — populated during fresh analysis via `ComputeBitUsage` (ffmpeg → s32le mono 30 s mid-track → trailing-zeros histogram). Null on legacy entries, ffmpeg-absent installs, and silent / undecodable files. **Detection-only valid for codec ∈ {flac, alac, wav, aiff} claiming `bitDepth ≥ 24`** — lossy decode floods the LSBs with reconstruction noise so the metric is meaningless for MP3/AAC/etc. Phase 3+5 `hfEnergyRatio` + `hfEnergyMethod` and `hfSpectralStructure` block — derived from a **single** ffmpeg-piped managed-FFT pass (`ComputeHfAnalysis`) over 30 s mid-track at the source's native sample rate. `hfEnergyRatio` is the fraction of audio energy above 22.05 kHz (Parseval-style energy-weighted across windows). `hfSpectralStructure` carries three FFT-derived discriminators: `flatness` (Wiener entropy of HF bins, range [0,1] — broadband = real, peaky = imaging artifact), `peakToMean` (max/mean HF mag², ratio — catches narrow spikes), `imagingSymmetry` (Pearson r of HF bins with their mirror about the original 22.05 kHz Nyquist, range [-1,1] — currently unused in the verdict; Lanczos suppression made it useless on corpus-1, kept for future tuning). Only populated when `sourceSampleRate > 44100` — no Nyquist headroom otherwise. Method tag `managed-fft-radix2-30s-mid-native`. Together with `bitUsage`, these are the independent fake-hi-res signals that dither evasion can't fabricate.
- **Identity** (nullable, omit-when-missing): `fileMd5` (whole-file MD5 — written only under `--file-md5` since 2026-07-11; without the flag, scans never write it (fan-out skips it, tier-2/4 refreshes drop it) and `--migrate` strips stored values; nothing consumes it — MBXHub indexes `audioStreamSha256` only), `fingerprint.v1` (composite, written via `WriteFingerprintV1` — its fields, the omit-when-0/empty rules and the nested `mp3LameTag` object (codec=mp3 with a Xing/Info+LAME header) are defined in that function), `audioStreamSha256` (ride-along in default Essentia mode via `ComputeAudioStreamSha256FromFile`; emitted in all three scan-path modes — MoodsMode, `--file-list`, `--analyze-file` — plus `--hash-only --level stream`). **FLAC hashes are frame-anchored since 2026-07-21** (`audioStreamSha256Source: "flac-frames"`, `GetFlacAudioStart` walks the metadata-block chain): TagLibSharp's invariant region for FLAC *includes* the metadata blocks, so a Vorbis-comment write (MBXHub's embedded mood field, any retag) drifted the old hashes even with byte-identical frames. The cache tiers and `--verify` compute the legacy TagLib-region sha in the same read pass and match stored pre-transition values against it, upgrading entries in place (`audioStreamSha256-upgraded`) with zero re-analysis; FLACs retagged *before* migrating can't be matched either way — `--verify --backfill --accept-flac-tag-drift` re-keys them when audio props still agree with the stored fingerprint. `fingerprint.v1.audioHead64kMd5` uses the same frame anchor for FLAC (`audioHead64kMd5Source: "flac-frames"`); `IsTagsOnlyChange` requires matching sources.
- **Housekeeping**: `lastModified`, `analysisDuration`.
- **Sony SMFM (12-TONE)** (nullable, omit-when-missing; **OFF by default since 2026-10-14** — parked dark, not removed: no consumer picks or matches on it and nothing decodes the slots, so `ResolveNoSmfm` reads it only under `--smfm` / config `smfm` / `--refresh-smfm`, with `--no-smfm` overriding and a typed `--smfm` beating a config `no-smfm` (`DropConfigArgsOverriddenBy`); existing blocks survive because the cache-hit carry-forward is unconditional. When on: read fresh on a cache MISS via `SmfmReader`, and **carried forward by `RebuildCacheEntryCore` on a cache HIT** rather than re-read — an unchanged mtime means the SMFM tag is unchanged too, so this skips a per-file network header open; `--refresh-smfm` forces a re-read on hits to backfill after a reader upgrade or bulk-tagging): `smfmScores` (raw STMO slot scores, `int[10]`, 0-255), `smfmChannel` (dominant raw STMO slot index = argmax — **NOT a mood channel**), `smfmChannelName` (**always null** — the slot→name labels were **device-refuted** on 2026-06-27: SMFM slots are not 1:1 with Sony's mood channels, which are 2-D arousal×valence regions; kept as a back-compat property), `smfmBpm` (Sony GBPM). **Renamed from the former `sensme*` keys on 2026-06-28** — the read path keeps a `sensme*` old-key fallback for un-migrated libraries, and `--migrate` rewrites existing files `sensme*→smfm*` (with backup). **Removal is `--strip-smfm` (2026-08-19), and it is a THIRD mode that can cost the operator data — but it removes FIELDS, not entries**, so it is not the `--prune-excluded` / `--fixup` removal class: every track and every other field survives. It exists because removal was a one-way door in the wrong direction — `ApplySmfmInPlace` returns early on an absent block, so `--refresh-smfm` backfills but structurally CANNOT clear, and `smfm-tools`' file-side strip deliberately preserves the audio frames (hence `audioStreamSha256`), so a stripped file takes a cache hit and the catalog keeps the stale scores forever. `SmfmJsonKeys` strips BOTH key generations — a `smfm*`-only strip would leave entries still reading as tagged through the `sensme*` fallback, and a self-test pins the stripper against the real reader for exactly that reason. Sidecar regeneration is **required, not cosmetic**: the hub boots sidecar-first from the `.mbxs`, so a JSON-only edit changes nothing at runtime. The default-off is what now makes a strip durable — SMFM is READ from file tags and never computed, so a scan with SMFM on refills the catalog on the next cache MISS; `--no-smfm` remains the override, guarded inside `ApplySmfmInPlace` rather than at the call sites, and refuses to combine with `--refresh-smfm`. Any interpreted `(arousal, valence)` signal belongs **downstream**, never in truedat (the hub's SMFM projector is retired). Format docs + extraction tooling: `smfm-tools/` (public, curated from local research). `--list-missing-smfm [path]` (read-only) lists entries with no SMFM block plus coverage → `mbxmoods-smfm-missing.csv`; it is deliberately **not** in the `--stats` Recommended block, because truedat only reads SMFM and never writes it — no truedat command closes that gap, and the advisor must only name gaps a command can fix (same rule as the d146a04 reachability fix).
- **Phase 4 verdict** (nested `truedat` object): `hiresGenuine` + `hiresConfidence`, `lossyTranscodeLikely` + `lossyTranscodeConfidence`, `method`. **The hi-res gate requires `sampleRate > 44100` as well as lossless + ≥24-bit (2026-08-28).** `ComputeHfAnalysis` bails at ≤44100, so without the rate term the panel decided on `lowestNonZeroBit` + `effectiveBits` alone — two bit-depth measures — and wrote `hiresGenuine: "yes"` for CD-rate files. Do not restore the codec+depth-only gate. **`prov: pad16` survives the closed gate**: padding is a bit-depth fact at any rate, and below the gate its confidence comes from the two bit-usage signals agreeing (`pad16` both, `pad16?` lnz alone). Computed inline at write time by `ComputeTruedatVerdict` from the already-extracted features; **not persisted in TrackEntry / cache** so threshold changes ship without rescan. Four-string enum (`"yes"` / `"no"` / `"unknown"` / `"n/a"`) — explicitly NOT a bool, because collapsing "unknown" into yes/no is what produces the false-positive/negative failures the verdict block was designed to avoid (see BACKLOG "Known detection challenges"). Two further optional keys since 2026-08-12: `prov` (provenance defect — `pad16` | `tc` | `up44` | `lossy`, joined with `+`) and `content` (a readable class other than music — `speech` | `silence` | `silence?`); both omit-when-empty. Block omitted when none of `hiresGenuine`/`lossyTranscodeLikely`/`speechLikely` reached a decided yes/no **and** neither `prov` nor `content` is set (legacy entries without fingerprint.v1, weird-codec files, or entries lacking enough signal). The `prov`/`content` half of that predicate is load-bearing: a content-silence-only track decides no yes/no axis, so an axes-only rule would suppress its own flag — the trap the 2026-08-12 review caught. Method tag identifies the algorithm/threshold generation — currently `truedat-v1-fft-rategate-2026-08-28` (corpus-1-calibrated), bumps again when a broader labeled corpus retunes the thresholds (Phase 4 corpus is the gating step in BACKLOG before the verdict can be considered tuned). Per-signal vote+weight trace emitted to stderr under `--audit`. **`speechLikely` (2026-07-22)** — same block, own fields (`speechLikely` + `speechConfidence` + `speechMethod`, tag `truedat-speech-v1.3-untuned-2026-08-13`): talk-vs-music classification computed at write time from stored features (danceability, chordsStrength, silenceRate30dB, zeroCrossingRate, bpmFirstPeakWeight, keyVotes strength). Write-time + not-persisted means it's retroactive across the whole catalog on the next save (any scan, cache hit or miss) with no rescan and no backfill tier needed. `"yes"` additionally gates on the zero-crossing signal firing so tone/ambient beds (which share talk's shape on the other signals) demote to `"unknown"` instead of a false `"yes"`. **This gate was originally load-bearing because `--migrate` pruned the catalog entry on `"yes"` — that purge was removed 2026-07-25 (Heuristics → Evidence Phase 3/4, `--migrate`'s speech purge deleted in `4b0c4fa`): `--migrate` now strips legacy fields only (`valence`/`arousal`, `audioMd5`, `chromaprint`, `chromaprintDuration`; `fileMd5` unless `--file-md5`; renames `sensme*`→`smfm*`) and never removes an entry on any verdict — speech-labelled, speech-likely, or otherwise.** `RecomputeSpeechLikely` is the JSON-facing twin of `ComputeTruedatVerdict`'s speech block, for a caller that only has a raw JSON node rather than a `TrackEntry`; as of 2026-07-25 it has **zero production callers** — its only caller was `--migrate`'s speech purge, and that purge is gone. It is kept, pinned by the self-test `list-speech recompute matches the TrackEntry path` (renamed 2026-07-25 from `migrate speech recompute matches the TrackEntry path` when its target moved), as the drift guard for any future JSON-only caller: `RecomputeSpeechLikely` reads exactly the verdict's input signals, so extend it whenever that list changes. **Rev-1.2 adds a second gate: `"yes"` also requires `danceability < 0.50`.** Sparse / live / free-form *instrumental* music craters on the whole rest of the panel exactly like speech (no tempo peak, weak chords, weak key, high silence, high zcr) — danceability is the one signal that separates them: measured 2026-07-22, genuine speech sits at 0.00 while real-music false positives ran 0.66–1.10. Without this gate the (now-removed) `--migrate` purge would have pruned Charlie Parker "Hot House", NIN "Burn" (live) and Travis "Outro". The 0.50 cut is deliberately tighter than the danceability signal's own talk-vote threshold (0.70) because the 0.50–0.70 band held real music (Beatles "Sgt. Pepper Effects Tape 2" 0.657, "For Lovers Only (Reprise)" 0.698) — the gate's margin costs no real recall against genuine speech (0.00) even though it no longer guards a destructive action. `--list-speech [path]` is the read-only review surface for the full `speechLikely == "yes"` set (`RunListSpeech`) — it lists **every** speech-yes entry regardless of genre label. Since 2026-07-28 (`4d8a60c`) `--stats` reports two DISJOINT lines instead of the old union count: `Speech (acoustic)` = recomputed `speechLikely == "yes"` and is **count-equal with `mbxmoods-speech.csv` by construction** (the live 1-vs-0 advisor mismatch this fixed), and `Speech (genre label)` = stored `genre == "Podcast"` but NOT acoustic-yes — invisible to `--list-speech`, so its advisor points at a genre rule (`kind:genre, value:Podcast`) instead. Each line only points at a surface that can show what it counted (the d146a04 advisor rule). Review the CSV, then add a rule to a decisions delta and run `--apply-exclusions`; the verdict is still `-untuned` (real ambient/spoken-intro music can reach `"yes"`).
