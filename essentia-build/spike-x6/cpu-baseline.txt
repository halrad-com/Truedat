== the architect's four follow-ups (mail 008) ==
FFT share. FFT (2 instances, OnsetRate's and the Degara tracker's) 0.61 s +
Spectrum (3 in network1, 1 in network2; Spectrum wraps an FFT) 1.16 + 0.38 s
= 2.15 s = 2.4% of total. CartesianToPolar (7.0 s) is atan2/hypot per bin, not
an FFT. So the FFTW AVX2/FMA and -march=x86-64-v3 toolchain levers address
2.4% of the extractor's CPU: closed with a number, like the JSON item.

HPCP sharing. Three instances take the same SpectralPeaks (60 peaks,
20-3500 Hz) and the same tuning frequency, with DIFFERENT parameters:
  hpcp_key    size 36,  bandPreset false, nonLinear false, windowSize 1.0, default harmonics
  hpcp_chord  size 36,  bandPreset true (split 500 Hz), nonLinear true, windowSize 0.5, harmonics 8
  hpcp_tuning size 120, otherwise = hpcp_chord
No two are parameter-identical, and a 36-bin HPCP is not a re-binning of the
120-bin one (cosine weighting over a 0.5-semitone window), so there is no
byte-identical dedupe. Closed.

Shared decode - what the four passes prepare (plan B4 sizing; no code here):
  phase 2  AudioLoader -> StereoDemuxer -> Resample L,R to 44.1 kHz ->
           StereoMuxer -> StereoTrimmer -> LoudnessEBUR128.
           STEREO, 44.1 kHz, unscaled.            cost: AudioLoader 1.6 + Resample 4.0 (two) = 5.7 s
  phase 3  EqloudLoader = MonoLoader (AudioLoader -> MonoMixer -> Resample) ->
           Trimmer -> Scale (the loader's default gain) -> EqualLoudness -> ReplayGain.
           MONO, 44.1 kHz, default scale, equal-loudness filtered.  cost 1.4 + 2.2 + 1.4 (EqualLoudness) = 5.1 s
  phase 4  EasyLoader = MonoLoader -> Trimmer -> Scale(replayGain from phase 3).
           MONO, 44.1 kHz, replay-gain scaled.    cost 1.8 + 2.2 = 4.0 s
  phase 5  EasyLoader with the SAME parameters as phase 4.
           IDENTICAL stream to phase 4's.         cost 1.6 + 2.1 = 3.7 s
Only phases 4 and 5 consume the same prepared audio; the second pass exists
because BeatsLoudness needs phase 4's beats_position and HPCP needs its
tuning_frequency. A PCM spool of phase 4's stream (mono float32 at 44.1 kHz:
176 KB per second, ~265 MB for a 25-minute track, RAM or stage dir) serves
phase 5 byte-identically: ~3.7 s, 4.2% of total, exactly. Phase 3's stream
differs only by a linear gain before a linear filter - derivable from phase
4's up to float rounding (not byte-identical); phase 2 is stereo and separate.
So: 19% in four passes; ~4% recoverable exactly, ~14% if rounding-level drift
in the replay gain pass is accepted (a refresh-decision input).

Onset methods (source: algorithms/rhythm/onsetrate.cpp, streaming composite).
OnsetRate runs ONE front end - FrameCutter 1024/512 (hann) -> FFT ->
CartesianToPolar (magnitude AND phase) - feeding TWO OnsetDetection instances
on the same frames, method "hfc" (magnitude only) and method "complex"
(magnitude + phase). The two detection functions are fused by the Onsets
algorithm with weights (1, 1) into one onset-time list, and
onset_rate = count / (frames x hop / sampleRate). So: dropping either method
changes onset_rate (a producer change: a product decision, not an optimisation);
dropping "complex" alone would also let the front end use Spectrum
(magnitude only) instead of CartesianToPolar - the phase (atan2 per bin) is
the expensive half of the 7.0 s. The Degara beat tracker has its own
FFT -> CartesianToPolar -> OnsetDetection(complex) front end on the same
audio (frame 1024 / hop 512 as well) - the third OnsetDetection instance.
The measured split between the three instances: per-method rows in the drop 2
report (x6profile keys by "method" / "size" from build-s2 on).

== what this says about the planned cuts ==
- The B2 cuts as planned act on aggregation (3.4%) and pool storage (1.7%) and
  one unread branch (MelBands 128: 0.42 s, 0.5%, plus its storage/aggregation
  share). Everything they can remove together is on the order of 5% of
  extractor CPU. They are still worth having (they are free and they shrink
  the output), but they are not where the time is.
- The time is in features truedat READS:
  * the onset front end - OnsetDetection x3 (OnsetRate's hfc+complex, the
    Degara beat tracker's complex) + CartesianToPolar x2 + FFT 0.6 =
    ~18.4 s, 21% of total - feeding rhythm.onset_rate, bpm, beats_position
    and the bpm histogram, all read;
  * HPCP x3: 8.2 s, 9% - key profiles, chords, tuning, all read;
  * decode + resample, FOUR times (phases 2,3,4,5): AudioLoader 6.4 s +
    Resample 10.5 s = 16.9 s, 19% of total. A shared decode (plan B4) would
    keep one pass: ~12.7 s, ~14%, recoverable. The plan's line for a .7 design
    was "if measured >= 20%": the four passes are 19%, the recoverable part 14%.
  * EBU R128: ~5.5 s, 6%, read (loudness_ebu128.*).
- B4's JSON double-check: the whole output phase is 1.1% of total, so the
  double parse is at most a fraction of that. Not worth a change.
- Instances: 66 PoolStorage sinks in network1 make 8.66M process() calls for
  1.5 s - the per-call scheduler cost (the 6.6 s remainder) scales with the
  number of algorithms in the graph, which is the drop 3 (fewer copies) and
  "fewer nodes" territory, not a profile switch.
